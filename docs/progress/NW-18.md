# NW-18 — Verifizierter simulierter Zahlungsablauf

- **Status:** Für den Testbetrieb implementiert und gegen PostgreSQL 18.6 geprüft am 30. Oktober 2026.
- **Basis:** NW-17 und [ADR-009](../adr/ADR-009-simulierte-zahlungen.md).
- **Grenze:** Es findet keine echte Zahlung statt. Die Mock-Routen sind nur bei `APP_ENV=development` aktiv.

## Umsetzung

Migration 11 speichert simulierte Zahlungen und Provider-Ereignisse. Debitkarte, Klarna, PayPal und Überweisung verwenden denselben simulierten Ablauf ohne Karten-, Bank- oder Zugangsdaten. Die Backend-API initiiert eine Zahlung nur für eine eigene Bestellung mit aktiver Reservierung. Wiederholte Initiierung derselben Zahlungsart liefert dieselbe Zahlungs-ID; ein Methodenwechsel wird abgewiesen.

Ein Ereignis wird über HMAC-SHA256, Zeitfenster und unveränderte JSON-Bytes geprüft. Die eindeutige Event-ID und ein Body-Hash verhindern eine zweite Wirkung bei Wiederholung. Erfolg markiert Reservierung und Bestellung als bezahlt; Fehler gibt den Bestand frei; eine Erstattung ändert den Zahlungsstatus, erhöht den Bestand aber nicht automatisch. Verspäteter Erfolg nach Reservierungsablauf wird als `manual_review` erfasst und verkauft keinen freigegebenen Bestand. Die Übergänge stehen auch im unveränderlichen `order_status_events`-Verlauf.

Die Bestellbestätigung bietet im Entwicklungsbetrieb die vier simulierten Arten und Schaltflächen für Erfolg, Fehler und Erstattung. Sie kennzeichnet alle Optionen als Simulation. Ein offener Auftrag kann dort storniert werden.

| Prüfung | Ergebnis |

| Erfolg, Fehler, Erstattung, Ablauf, Stornierung mit spätem Fehler | PASS: Bestell- und Bestandszustände bleiben konsistent |

| Angular-Bestätigungsseite: PayPal wählen und Erfolg simulieren | PASS: Komponententest mit echten HTTP-Anfrageverträgen |
| Isolierte laufende API mit PostgreSQL 18.6 und Caddy | PASS: Testbestellung erstellt, PayPal doppelt idempotent initiiert, Erfolg simuliert; `GET /orders` meldete `PAID` und die Browseransicht zeigte „PayPal · Simuliert bezahlt“ |
| Migration 11 `up/down/up` in leerer separater Datenbank | PASS |

Der Backend-HTTP-Test lief gegen eine separate lokale PostgreSQL-18.6-Testdatenbank (`NORDWINDS_MOCK_PAYMENT_TEST_URL`). `npm test -- --watch=false --include=src/app/features/checkout/pages/order-confirmation/order-confirmation.spec.ts` meldete drei bestandene Tests; die gesamte Angular-Suite 94 bestandene Tests. `npm run typecheck`, `npm run lint`, `npm run format:check` und `npm run build` bestanden. Die laufende Vorschau verwendete ausschließlich temporäre Container und einen synthetischen Testkunden; sie wurde danach entfernt. Ein echter Zahlungsanbieter, dessen Sandbox und ein Live-Verkaufsablauf sind durch diesen Mock nicht abgedeckt.
