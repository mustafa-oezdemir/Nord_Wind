# NW-17 — Bestandsreservierung und paralleler Checkout

- **Status:** Implementiert und gegen PostgreSQL 18.6 geprüft am 30. Oktober 2026.
- **Basis:** NW-16 (`7827bd5`), [ADR-010](../adr/ADR-010-bestandsreservierung.md).

## Umsetzung

Migration 10 legt `order_reservations` mit Menge, Frist und den Zuständen `active`, `consumed` und `released` an. `orders.Repository.Create` erstellt Bestellung, Positions-Snapshots, Statusverlauf und Bestandsreservierung in einer Transaktion. Varianten werden in stabiler ID-Reihenfolge mit einem bedingten atomaren `UPDATE` abgebucht. Bei einem Fehler rollt auch ein zuvor abgebuchter Teil des Warenkorbs zurück.

Die Standardfrist beträgt 15 Minuten. Ein Worker gibt abgelaufene Reservierungen alle 30 Sekunden frei. Ohne initiierte Zahlung wird die Bestellung `CANCELLED`, mit offener Zahlung `PAYMENT_FAILED`. `POST /api/v1/orders/{orderNumber}/cancel` erlaubt dem Besitzer, eine offene Bestellung zu stornieren. Wiederholte Stornierung gibt den Bestand nicht doppelt frei. Bezahlte Bestellungen können auf diesem Weg nicht storniert werden.

PostgreSQL-Deadlocks (`40P01`) und Serialisierungsfehler (`40001`) wiederholen höchstens dreimal die vollständig zurückgerollte Transaktion. Der Checkout führt keine E-Mail oder externe Zahlung innerhalb des Retry-Blocks aus. Der Bestand bleibt durch die Datenbankbedingung und den vorhandenen Nichtnegativ-Constraint geschützt.

## Prüfung

| Prüfung | Ergebnis |
| --- | --- |
| Zwei gleichzeitige `POST /api/v1/orders` verschiedener Kunden für das letzte Stück | PASS: genau ein `201`, ein `409 CART_CHANGED`, Bestand 0 |
| Gewinner storniert zweimal; anderer Kunde versucht denselben Schlüssel erneut | PASS: Bestand einmal freigegeben, erneuter Checkout `201` |
| Mehrteiliger Warenkorb, zweite Position ausverkauft | PASS: erste Abbuchung zurückgerollt, keine Teilreservierung |
| Ablauf, verspäteter Erfolg, bezahlte Bestellung, echter PostgreSQL-Deadlock | PASS: keine negative Menge, keine doppelte Freigabe, Retry erfolgreich |
| Migration 10 `up/down/up` in leerer separater Datenbank | PASS |

Der PostgreSQL-Lauf verwendete vier getrennte temporäre Datenbanken mit Namen `nordwinds_test_*` in einem lokalen PostgreSQL-18.6-Container. Die Tests liefen mit `NORDWINDS_INVENTORY_TEST_URL`, `NORDWINDS_ORDERS_TEST_URL` und `NORDWINDS_MIGRATION_TEST_URL`; `go test` meldete für `internal/inventory`, `internal/server` und `internal/migrations` jeweils `ok`.
